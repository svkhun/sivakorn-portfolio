01 // Problem & My Role

Financial decisions need context

K-NEXUS explores two questions for first jobbers: what remains after bills and a chosen reserve, and what deserves review before sending money. It is an independent hackathon-context prototype, not an official KBank/KBTG product or an endorsed banking service.

02 // FlowSense · Application Baseline

An explainable plan, with ML disabled

The documented Application uses HISTORY_MEAN → SCENARIO → ABSTAIN. It averages non-bill spending when at least seven complete, known days exist in a 28-day window. A known zero-spending day counts; missing and partial days do not become zero.

Without sufficient history, a valid versioned scenario can supply the spending basis. Default synthetic non-bill assumptions are 350 / 600 / 300 THB per day for the three personas. Without history or a valid scenario, the system abstains. These are assumptions, not measured customer spending.

Bills, reserves, the spending outlook, simulated saving capacity, and transfer review share this basis. Savings require opt-in and a user action; standard simulated withdrawals remain available. FlowSense ML remains disabled. A baseline projection is not a validated 30-day ML forecast.

03 // TrustGraph · Implementation

Stored graph context, classifier, and separate policy

The research pipeline builds a past-only transaction graph using channel and reverse-channel relations. Node inputs come from past degree and transferred amounts. A self-supervised R-GCN produces 16-dimensional account embeddings without reading timeless mule labels.

The Application combines stored recipient embeddings with transaction telemetry and authentication features for LightGBM inference through ONNX Runtime. The GNN is computed offline rather than on every request. An unknown recipient can lack graph context; missing context does not mean safe.

Model scores are distinct from synthetic blacklist and review policies. Eligible risky scenarios use a cooldown and simulated authentication; a policy block is not evidence that the model intercepted a real scam. Authentication and all transfers remain simulated.

05 // Application, Showcase & Boundaries

Keep runtime, research, and outcomes separate

Application: React and FastAPI own the synthetic session, bill/reserve/savings rules, model-package loading, and transfer-review workflow. Showcase: a separate presentation and research repository owns training, evaluation, and artifact export. Research results are not activated automatically.

Kafka, Feast, and Triton are proposed scaling components, not established parts of this documented serving path. Earlier local latency figures are not current production SLAs. No realized CASA growth, prevented losses, real-user benefit, or production banking readiness is established.

The historical 30 October 2026 audit recorded Ready for demo with limitations. That is dated release evidence, not a fresh live verification. The local Showcase README and the historical deployed release differ on legacy POST routes; this case does not claim the current live backend is entirely read-only.
